# ゲーム開発ワークフロー v2(個人開発 × AI協働 × Godot 2D)

> **人間が読む「進め方の型」**。エージェントが毎回読む指示は `AGENTS.md` に分けてある。
> 対象:個人開発、Godot 4(GDScript のみ)、2D。
> ツール:DeepSeek Harness(dsh)/ Cline / Claude。

---

## 0. このテンプレートの使い方

1. このフォルダごとコピーして新しいプロジェクトを始める
2. `game/` に Godot でプロジェクトを作成する(`game/project.godot` ができる)
3. `AGENTS.md` の「プロジェクト概要」を埋める
4. 下の「3. フェーズ」を Phase 0 から順に進める
5. 各フェーズの **ゲート(完了条件)をすべて満たすまで次に進まない**

### ファイル構成

```
project_root/
├── AGENTS.md                 # エージェント共通指示(dsh・Cline が自動で読む)。短く保つ
├── GAME_DEV_WORKFLOW.md      # このファイル。人間用の進め方
├── .gitignore / .gitattributes
├── .agents/skills/           # スキル(定型作業の手順書)。dsh・Cline が自動で読む
│   ├── session-handoff/      # セッションの開始・終了手順
│   ├── review-gdscript/      # AI生成コードのレビュー
│   ├── write-test/           # テストの書き方
│   └── add-data-content/     # データ駆動コンテンツの追加(例)
├── docs/
│   ├── design.md             # 何を作るか(設計書)
│   ├── architecture.md       # どう作るか(規約)
│   ├── gdscript_pitfalls.md  # Godot 4 の落とし穴・AIがよく間違える点
│   ├── commands.md           # 実行・テスト・エクスポートのコマンド
│   ├── agent_ops.md          # AIエージェント運用ガイド
│   ├── skill_template.md     # 新しいスキルを作るときの雛形
│   ├── decisions.md          # 決定記録
│   ├── progress.md           # 進捗・申し送り
│   ├── backlog.md            # タスク一覧
│   ├── playtest.md           # プレイテスト記録
│   ├── bugs.md               # バグ一覧
│   └── release_checklist.md  # リリース前チェック
├── game/                     # Godot 本体プロジェクト
└── prototype/                # 使い捨てプロトタイプ用(別の Godot プロジェクト)
```

`prototype/` は `game/` とは別の Godot プロジェクトにする。混ぜるとプロトタイプの雑なコードが本体に紛れ込む。

## 1. 基本原則

1. **縦に薄く、横に全部通す** — 全システムを最低限でつないでから肉付けする
2. **作らないものを先に決める** — スコープ外リストは必須
3. **規約が先、コードは後** — エージェントは規約にないことを決めない。決めるのは人間
4. **スキルは抽出するもの** — 同じ作業を2〜3回やってから手順書にする
5. **1タスク = 1目的 = 1コミット** — エージェントに渡す単位は「30分〜2時間で人間が確認できる量」
6. **決定は記録する** — 同じ議論を2回しない
7. **機械で確かめる** — テスト + 警告をエラー扱い + 毎回の通しプレイ
8. **面白さは人間が判断する** — AIは作業者。面白いかどうかの判断は委ねない
9. **エンジンのバージョンは固定する** — プロジェクト途中でメジャー/マイナー更新しない

## 2. 役割分担

| 役割 | 担当 | 主な仕事 | 渡すもの |
|---|---|---|---|
| 判断 | 人間 | 面白さ、スコープ、最終確認、マージ | — |
| 設計・監督 | Claude | 設計書・規約・スキルの作成、コードレビュー、詰まったときの相談 | 該当ファイルの内容、エラー全文 |
| 量産実装 | DeepSeek Harness | スキルに沿った実装、まとまった作業 | タスク依頼テンプレート + スキル名 |
| 現場作業 | Cline | エディタ上の修正、デバッグ、小さな調整 | 対象ファイルとエラー |

詳細な運用(コンテキスト管理、受け渡し、失敗パターン)は `docs/agent_ops.md` を参照。

## 3. フェーズ

### 全体像

| フェーズ | 目的 | 目安期間(個人) | 主に使うツール |
|---|---|---|---|
| 0 構想 | 何を作るか・作らないかを決める | 2〜5日 | 人間 + Claude |
| 1 プロトタイプ | 面白いか確かめる | 1〜2週間 | Cline / dsh(速度優先) |
| 2 基盤 | プロジェクトの土台と規約を固める | 3〜5日 | Claude → Cline |
| 3 縦切り | 全システムを1本につなぐ | 2〜4週間 | dsh / Cline |
| 4 スキル抽出 | 量産できる状態にする | 1週間 | Claude |
| 5 量産(α) | コンテンツとシステムを揃える | 最長 | dsh(量産)/ Claude(レビュー) |
| 6 仕上げ(β) | 品質を上げる | 全体の25〜30% | 全員 |
| 7 リリース | 出す・直す | — | 人間 |

期間は目安。**合計見積もりが自分の想定の2倍を超えたら、スコープを削る**(5.3 参照)。

### Phase 0:構想

**目的**:作るものと作らないものを確定する。

作業:
- [ ] `docs/design.md` の「コンセプト」「デザインの柱」「コアループ」を埋める
- [ ] **デザインの柱を3つまで**決める(迷ったときの判断基準。例:「1プレイ15分」「毎回違う展開」「操作はボタン2つ」)
- [ ] コアループを1文で書く
- [ ] 機能を MoSCoW(Must / Should / Could / Won't)で分類する
- [ ] Won't(スコープ外)を5項目以上書く
- [ ] プロトタイプで確かめる「問い」を1〜3個書く(例:「敵の群れを避けながら拾う操作は気持ちいいか?」)
- [ ] 締め切りを決める(Phase 3 完了日。個人開発では締め切りがないとスコープが膨らむ)

Claude の使い方:
- 設計書の穴を指摘させる(「この設計で矛盾している点、決まっていない点を挙げて」)
- 似たゲームを挙げさせ、差別化ポイントを言語化する

**ゲート**:
- [ ] コアループを1文で言える
- [ ] デザインの柱が3つ以内で決まっている
- [ ] Won't リストがある
- [ ] プロトタイプで確かめる問いがある

### Phase 1:プロトタイプ

**目的**:Phase 0 の「問い」に答える。それ以外はやらない。

作業:
- [ ] `prototype/` に Godot プロジェクトを作る
- [ ] 問いに答えるための最小限だけ作る(図形・仮素材、規約無視でよい)
- [ ] 自分で 10 回以上遊ぶ。可能なら他人に 1 人以上遊んでもらう
- [ ] `docs/playtest.md` に記録する(テンプレートあり)
- [ ] 結論を `docs/decisions.md` に書く:**続行 / 方向修正 / 中止**

時間の上限を先に決めておく(例:2週間)。上限を超えても答えが出ないなら、問いが大きすぎる。

**ゲート**:
- [ ] すべての問いに答えが出た
- [ ] 「続行」の判断が decisions.md にある(方向修正なら Phase 0 へ、中止なら別の企画へ)

### Phase 2:基盤

**目的**:エージェントが迷わず作業できる土台を作る。ここを丁寧にやるほど、後の AI 作業の精度が上がる。

作業:
- [ ] Godot のバージョンを決めて固定する(`AGENTS.md` と `architecture.md` に明記)
- [ ] `game/` に Godot プロジェクトを作成
- [ ] Git を初期化し、`.gitignore` / `.gitattributes` を確認して最初のコミット
- [ ] プロジェクト設定(`docs/architecture.md` の「プロジェクト設定」を参照)
  - [ ] 表示解像度・ストレッチモード(ピクセルアートなら viewport + 整数倍スケール)
  - [ ] 入力アクション(InputMap)を定義
  - [ ] 物理レイヤー名を定義
  - [ ] GDScript 警告:`untyped_declaration` などをエラー扱いに
- [ ] テストフレームワーク(GUT か gdUnit4 のどちらか)を導入し、サンプルテストを1本通す
- [ ] `docs/commands.md` のコマンドを自分の環境で実行し、動くことを確認
- [ ] `docs/architecture.md` を埋める(Claude と相談しながら)
- [ ] 必要なら Godot MCP サーバーを Cline に接続(`docs/agent_ops.md` 参照)
- [ ] 試しに小さなタスクを1つエージェントに依頼し、規約通りのコードが出るか確認する

**ゲート**:
- [ ] テストがコマンド1つで実行できる
- [ ] architecture.md が埋まっている
- [ ] エージェントに小タスクを依頼して、規約通りの結果が返ってきた

---

### Phase 3:縦切り(バーティカルスライス)

**目的**:全システムを最低限の形で1本につなぐ。見た目は仮でよい。

つなぐもの(ジャンルに応じて増減):
- [ ] 起動 → タイトル → 本編 → リザルト/ゲームオーバー → タイトル のシーン遷移
- [ ] プレイヤー操作(入力 → 移動 → アニメーション)
- [ ] コアループの1サイクル(敵1種、アイテム1種、マップ1つ など)
- [ ] データ駆動の仕組み(敵・アイテムのパラメータを Resource で定義)
- [ ] UI:HUD 1画面、ポーズメニュー 1画面
- [ ] セーブ/ロード(バージョン番号付き。`architecture.md` 参照)
- [ ] 設定(音量、フルスクリーン)の保存
- [ ] サウンド:BGM 1曲、SE 数個が鳴る仕組み(オーディオバス設定込み)
- [ ] エクスポートして、エディタ外で起動できることを確認

進め方:
- 依存関係の少ない順に `docs/backlog.md` に積み、1タスクずつ進める(5章のタスクサイクル)
- この段階では **各作業を「2回目にやるときのために」メモしておく**(Phase 4 の材料)

**ゲート**:
- [ ] エクスポートしたビルドで、最初から最後まで通しで遊べる
- [ ] セーブ → 終了 → 再起動 → ロードで状態が戻る
- [ ] テストがすべて通る
- [ ] 警告ゼロ

---

### Phase 4:スキル抽出

**目的**:繰り返す作業を手順書にして、エージェントに量産させられる状態にする。

作業:
- [ ] Phase 3 のメモから、今後何度も繰り返す作業を洗い出す
  - 例:敵の追加 / アイテムの追加 / ステージの追加 / UI画面の追加 / 会話イベントの追加 / SEの追加
- [ ] 1つずつスキル化する:
  1. 2回目の実装を **自分(または Cline と対話しながら)** 行い、手順を `.agents/skills/<名前>/SKILL.md` に書く(`docs/skill_template.md` を使う)
  2. 3回目は **スキル名だけを渡して** dsh に実装させる
  3. 間違えた箇所をスキルの「よくある失敗」と手順に反映する
  4. もう一度やらせて、修正なしで通れば完成
- [ ] スキルに合わせて、ベースシーン(`_base_enemy.tscn` など)やデータ型(`EnemyData`)を整える

**ゲート**:
- [ ] 主要な定型作業がスキル化されている
- [ ] 各スキルについて、エージェントが修正なしで1回成功した

---

### Phase 5:量産(α)

**目的**:`design.md` の Must と Should をすべて入れる。

作業:
- [ ] backlog.md の優先順にタスクサイクルを回す
- [ ] **週1回** 定期レビュー(6章)
- [ ] **2週に1回** プレイテスト(`docs/playtest.md`)
- [ ] 新しい種類の作業が2〜3回出たらスキル化
- [ ] バグは見つけたら `docs/bugs.md` に記録(その場で直すのは S1/S2 のみ)

α の終わりに **機能凍結**:新機能は追加しない。以降は内容と品質だけ。

**ゲート(α完了)**:
- [ ] Must と Should がすべて入っている
- [ ] 通しで最後まで遊べる
- [ ] S1(進行不能・クラッシュ)バグがゼロ

---

### Phase 6:仕上げ(β)

**目的**:遊べるものを「出せるもの」にする。個人開発で最も見積もりが甘くなる工程。全体の 25〜30% を見込む。

作業:
- [ ] 仮素材の差し替え(グラフィック、サウンド、フォント)
- [ ] 手触りの調整(ヒットストップ、画面揺れ、SE、パーティクルなど)
- [ ] バランス調整(数値は Resource に集約済みのはず。必要なら表計算で管理)
- [ ] チュートリアル / 導入部分
- [ ] バグ修正(S1 → S2 → S3 の順)
- [ ] パフォーマンス確認(想定する最低スペック環境で)
- [ ] 外部の人にプレイしてもらう(最低3人)
- [ ] `docs/release_checklist.md` を進める

**ゲート(β完了)**:
- [ ] S1・S2 バグがゼロ
- [ ] release_checklist.md の必須項目がすべて完了

---

### Phase 7:リリース・運用

- [ ] ビルドを作り、配布先(itch.io / Steam など)に提出
- [ ] Git にリリースタグを付ける(例:`v1.0.0`)
- [ ] リリース後のバグ報告を bugs.md に集約し、パッチを出す
- [ ] 振り返り:何がうまくいき、何が詰まったか。**このテンプレート自体を更新する**

## 4. 1日・1セッションの流れ

1. **開始**:エージェントに `session-handoff` スキルで開始させる(progress.md を読んで状況を要約させる)
2. **選ぶ**:backlog.md から今日のタスクを1〜3個選ぶ
3. **回す**:タスクサイクル(5章)
4. **終了**:`session-handoff` スキルで終了させる(progress.md に申し送りを書かせる)
5. **コミット**:人間が差分を確認してコミット

セッションの区切りでコンテキストを捨てるのが基本。長く続いたセッションほどエージェントの精度が落ちる。

## 5. タスクの扱い

### 5.1 タスクサイクル

1. **選ぶ** — backlog.md から1つ。大きければ分割(目安:変更ファイル 5 個以内)
2. **ブランチ** — `git switch -c task/<短い名前>`(作業前の状態に戻れるようにする)
3. **依頼** — 5.2 のテンプレートで依頼。関係するスキル名を必ず書く
4. **実装** — エージェントが実装・テスト実行
5. **確認** — 人間が `git diff` を見る + 実際にプレイして確認
6. **レビュー** — 大きな変更や重要な仕組みは Claude にレビューさせる(`review-gdscript` スキル)
7. **取り込み** — main にマージ(個人開発なら `git merge` でよい)
8. **記録** — progress.md 更新、必要なら decisions.md
9. **改善** — スキルや規約に抜けがあれば、その場で直す

うまくいかなかったら **ブランチごと捨ててやり直す**。直しを重ねるより、依頼文を改善して最初からやらせた方が早いことが多い。

### 5.2 タスク依頼テンプレート

~~~markdown
## タスク:<一言で>

### 使うスキル
- .agents/skills/<スキル名>(なければ「なし」)

### 背景
- <なぜやるのか。1〜2行>

### やること
- <具体的に。数値や名前は確定させて書く>

### やらないこと
- <触ってほしくないファイル・範囲>

### 完了条件
- [ ] <動作として確認できる条件>
- [ ] テストを追加し、全テストが通る
- [ ] 警告ゼロ

### 参考
- <参考にする既存ファイル>
~~~

### 5.3 スコープ管理

- 新しいアイデアは **すぐ実装せず** backlog.md の「アイデア置き場」に入れる
- 月に1回、backlog を見直し、Could は容赦なく Won't に移す
- 「あと少しで面白くなる」と感じたら、機能追加ではなく **既存要素の調整** から試す
- 遅れが出たら、締め切りではなくスコープを動かす

### 5.4 バグの扱い

| 重要度 | 内容 | 対応 |
|---|---|---|
| S1 | クラッシュ、進行不能、セーブ破損 | 最優先。即日対応 |
| S2 | 主要機能が正しく動かない | 今の作業が終わったら対応 |
| S3 | 見た目の崩れ、軽微な不具合 | まとめて対応 |
| S4 | 改善案レベル | backlog へ |

バグを直したら、**同じバグを検出するテストを1本足す**(可能な場合)。

## 6. 定期レビュー(週1回)

Claude に以下を依頼する(コードや docs を渡す)。

- [ ] 規約違反、Godot 3 的な書き方が紛れていないか
- [ ] Autoload やグローバルな参照が増えすぎていないか

- [ ] スコープが膨らんでいないか(design.md の Won't と照合)
- [ ] スキル化すべき繰り返し作業はないか
- [ ] スキルの手順が実装とずれていないか
- [ ] AGENTS.md が長くなりすぎていないか(目安 100 行以内)
- [ ] backlog の優先順位は妥当か

## 7. 詰まったときの対処表

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| エージェントが Godot 3 の書き方をする | 前提が伝わっていない | `gdscript_pitfalls.md` を読ませる。間違いを追記する |
| 規約からずれたコードが出る | 規約が曖昧 / 長すぎて読まれていない | 具体例を足す。AGENTS.md を短くする |
| 同じ説明を何度もしている | スキル化のタイミング | スキルを作る |
| 修正すると別の場所が壊れる | 依存が強すぎる / テスト不足 | シグナル化、テスト追加 |
| エージェントが関係ないファイルまで変える | 依頼範囲が曖昧 | 「やらないこと」を書く。タスクを小さくする |
| 直しても直しても動かない | 依頼が大きすぎる / 前提が間違っている | ブランチを捨てて依頼をやり直す。Claude に設計相談 |
| 作業が終わらない・広がる | スコープ過大 | 分割する。Won't に送る |
| 面白くない | コアループの問題 | 肉付けを止める。プロトタイプの考え方で調整を試す |
| モチベーションが落ちた | 成果が見えない | 通しで遊べるビルドを作って遊ぶ。小さな見た目の改善を1つ入れる |
